# Implementation Roadmap & Acceptance Criteria

Each phase ends with: tests passing (`pnpm test`, `cargo test`), lint/typecheck clean, and an independent review pass (not just the implementing subagent's own report) before moving on.

| #   | Phase                       | Key acceptance criteria                                                                                                                                                                                                                                                                       |
| --- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2   | Project init                | `pnpm dev` launches a Tauri window; empty SQLite DB created + first migration applied; `ci.yml` runs and passes on an empty test suite.                                                                                                                                                       |
| 3   | Core data                   | Full CRUD (via Tauri commands + UI forms) for raw materials, suppliers, purchase records; price history never overwritten (append-only verified by test); login/logout works with Argon2id; invalid input rejected with field-level errors.                                                   |
| 4   | Costing engine              | All scenarios in `costing-engine.md` §5 covered by passing unit tests; nested-recipe example from §12 reproduces the exact documented numbers; cycle detection rejects a constructed A→B→A case with a descriptive error.                                                                     |
| 5   | UI                          | Dashboard + all 8 nav sections navigable; recipe cost breakdown screen matches the §12.4 table format; destructive actions (archive/delete) require confirmation.                                                                                                                             |
| 6   | Local backup                | Create/list/restore backup round-trips a non-trivial DB losslessly (verified by test: create data → backup → wipe DB → restore → assert data identical); restore takes a pre-restore safety backup automatically; corrupted/tampered backup file is rejected with a clear error, not a crash. |
| 7   | Cloud (Dropbox)             | OAuth PKCE flow completes end-to-end against a real Dropbox test account; upload/list/download/delete all exercised by an integration test (or clearly marked manual test script if CI can't hold live OAuth secrets); Google Drive stub documented, not silently half-working.               |
| 8   | CI/CD & packaging           | A tagged pre-release produces installable artifacts for Windows, macOS, and Linux from GitHub Actions; artifacts actually install and launch on each OS (verified manually at least once before calling this done).                                                                           |
| 9   | Auto-updates                | A test release with an intentionally lower version number is detected as "update available" by a build with a higher version; a tampered `latest.json`/binary is rejected by signature check; toggling all three update settings off/on behaves as documented.                                |
| 10  | Security & final validation | `cargo audit` / `pnpm audit` clean or issues triaged and documented; no secrets in git history; final report delivered per requirement §27.                                                                                                                                                   |

Phase 1 (this document set) and its risk items are the only gate before Phase 2 begins.
